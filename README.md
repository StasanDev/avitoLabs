# TripGo — лабораторная работа 1

HTTP-сервис управления поездками. В рамках первой лабораторной работы сервис
принимает запросы по OpenAPI-контракту, хранит поездки в PostgreSQL и атомарно
записывает историю изменения их статуса.

Источник истины для HTTP API —
[`contracts/openapi/trip-service.openapi.yaml`](contracts/openapi/trip-service.openapi.yaml).
Типы и серверные интерфейсы генерируются из него и вручную не редактируются.

## Что реализовано

- создание, получение и завершение поездки;
- проверка входного JSON, обязательных полей, UUID, координат и цены;
- ошибки документированных trip-операций в формате `application/problem+json`;
- PostgreSQL через `pgxpool`, запросы через `squirrel`;
- атомарная запись поездки и истории статусов при создании и завершении;
- защита от двух активных поездок одного водителя;
- безопасное конкурентное завершение поездки;
- `/health` без обращения к БД и `/ready` с проверкой PostgreSQL;
- конфигурация только через переменные окружения;
- таймауты HTTP-сервера и запросов к БД;
- graceful shutdown по `SIGINT` и `SIGTERM` с единым бюджетом времени;
- идемпотентное создание поездки по `Idempotency-Key` — бонус ЛР1;
- multi-stage Docker-образ на distroless с запуском не от root — бонус ЛР1.

## Требования

- Go `1.27.1`;
- GNU Make;
- `tripgoctl` с локальным окружением курса или доступный PostgreSQL;
- `curl` — необязательно, для ручной проверки API;
- Docker — необязательно, только для проверки задания со звёздочкой.

Go-инструменты `goose` и `oapi-codegen` объявлены в `go.mod`, поэтому отдельно
устанавливать их не требуется. Команды ниже выполняются из корня репозитория в
WSL. В текущем окружении нужная версия Go установлена в `/usr/local/go`; перед
работой добавьте её в `PATH` и проверьте выбранный бинарник:

```bash
export PATH="/usr/local/go/bin:$PATH"
go version   # go version go1.27.1 linux/amd64
```

Если `go version` уже показывает Go `1.27.1`, изменять `PATH` не нужно.

## Быстрый запуск

В репозитории уже находится `environment.toml` для лабораторной работы 1.
Поднимите инфраструктуру:

```bash
tripgoctl cluster start       # один раз на машине
tripgoctl environment start
tripgoctl connect
```

`tripgoctl environment start` создаёт локальный `.env` с актуальным адресом
PostgreSQL. Файл не коммитится. Если используется собственный PostgreSQL,
скопируйте `.env.example` в `.env` и замените `DATABASE_URL`.

`Makefile` читает `.env` и экспортирует переменные дочерним процессам. Сам
бинарник `.env` не загружает: при прямом запуске без `make run` переменные нужно
предварительно экспортировать в окружение.

Примените миграции и запустите сервис:

```bash
make migrate
make run
```

При `HTTP_ADDR=:8080`, как в `.env.example`, сервер доступен на
`http://localhost:8080`:

```bash
curl -i http://localhost:8080/health
curl -i http://localhost:8080/ready
```

`/health` возвращает `200`, пока процесс работает. `/ready` выполняет `Ping`
PostgreSQL и возвращает `503`, если база недоступна.

## Конфигурация

Все перечисленные переменные обязательны: встроенных значений по умолчанию у
сервиса нет. Значения длительности задаются в формате
[`time.ParseDuration`](https://pkg.go.dev/time#ParseDuration), например `3s`,
`10s` или `30m`, и вместе с размерами пула должны быть положительными.

| Переменная | Пример | Назначение |
|---|---:|---|
| `HTTP_ADDR` | `:8080` | Адрес HTTP-сервера |
| `LOG_LEVEL` | `info` | Обязательный параметр, зарезервированный для настройки логирования в ЛР2 |
| `SHUTDOWN_TIMEOUT` | `10s` | Общий бюджет graceful shutdown |
| `IDEMPOTENCY_TTL` | `24h` | Срок валидности ключа идемпотентности для повторного запроса |
| `HTTP_READ_TIMEOUT` | `30s` | Максимальное время чтения запроса |
| `HTTP_READ_HEADER_TIMEOUT` | `5s` | Максимальное время чтения HTTP-заголовков |
| `HTTP_WRITE_TIMEOUT` | `30s` | Максимальное время записи ответа |
| `HTTP_IDLE_TIMEOUT` | `60s` | Таймаут keep-alive соединения |
| `DATABASE_URL` | `postgres://tripgo:tripgo@localhost:5432/tripgo?sslmode=disable` | Строка подключения к PostgreSQL |
| `DATABASE_MAX_CONNS` | `10` | Максимальный размер пула; должен быть положительным |
| `DATABASE_MIN_CONNS` | `2` | Минимальный размер пула; должен быть положительным |
| `DATABASE_MAX_CONN_LIFETIME` | `30m` | Максимальное время жизни соединения |
| `DATABASE_CONNECT_TIMEOUT` | `5s` | Таймаут подключения и стартового `Ping` |
| `DATABASE_QUERY_TIMEOUT` | `3s` | Таймаут запросов, readiness и операций с транзакцией |

Дополнительно проверяется, что `DATABASE_MAX_CONNS` не меньше
`DATABASE_MIN_CONNS`. При старте сервис выполняет `Ping` с
`DATABASE_CONNECT_TIMEOUT` и не запускается, если PostgreSQL недоступен.
Актуальный шаблон находится в [`.env.example`](.env.example).

## HTTP API

| Метод | Путь | Успешный ответ | Назначение |
|---|---|---:|---|
| `POST` | `/api/v1/trips` | `201`; `200` при idempotency replay | Создать поездку |
| `GET` | `/api/v1/trips/{tripId}` | `200` | Получить поездку |
| `POST` | `/api/v1/trips/{tripId}/finish` | `200` | Завершить поездку |
| `GET` | `/health` | `200` | Проверить процесс без обращения к БД |
| `GET` | `/ready` | `200` или `503` | Проверить доступность PostgreSQL |

Пример создания поездки:

```bash
curl -i -X POST http://localhost:8080/api/v1/trips \
  -H 'Content-Type: application/json' \
  -d '{
    "user_id": "5cb72c04-7650-45c9-a79b-bcdba0631e0c",
    "driver_id": "8860b315-ec86-42eb-a17c-7c163d721ff5",
    "start_point": {"latitude": 59.9398, "longitude": 30.3146},
    "end_point": {"latitude": 59.929, "longitude": 30.3626},
    "price": 1450
  }'
```

Для новой поездки сервис возвращает `201 Created` и заголовок `Location`. Ошибки
trip-операций имеют `Content-Type: application/problem+json` и стабильный
машиночитаемый `code`:

| HTTP | `code` | Когда возвращается |
|---:|---|---|
| `400` | `invalid_request` | Некорректное тело, UUID пути или `Idempotency-Key` |
| `404` | `trip_not_found` | Поездка не найдена |
| `409` | `trip_completed` | Поездка уже завершена |
| `409` | `driver_busy` | У водителя уже есть активная поездка |
| `409` | `idempotency_conflict` | Ключ повторно использован с другим телом |
| `500` | `internal_error` | Внутренняя ошибка без утечки деталей БД |

Ответы `GET /health` и `GET /ready` имеют `Content-Type: application/json`:
`{"status":"ok"}` для доступного сервиса и `{"status":"unavailable"}` с
кодом `503`, если PostgreSQL недоступен.

### Идемпотентное создание

`Idempotency-Key` — необязательный UUID, который генерирует клиент и передаёт в
заголовке `POST /api/v1/trips`:

```bash
curl -i -X POST http://localhost:8080/api/v1/trips \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: 7f1c2a54-6d0e-4a3b-9f21-0c8e5b3a77d1' \
  -d '{
    "user_id": "5cb72c04-7650-45c9-a79b-bcdba0631e0c",
    "driver_id": "8860b315-ec86-42eb-a17c-7c163d721ff5",
    "start_point": {"latitude": 59.9398, "longitude": 30.3146},
    "end_point": {"latitude": 59.929, "longitude": 30.3626},
    "price": 1450
  }'
```

| Запрос | Результат |
|---|---|
| Первый запрос с ключом | `201`, новая поездка и `Location` |
| Тот же ключ и побайтово то же тело | `200`, та же поездка с тем же `id` |
| Тот же ключ и другое тело | `409 idempotency_conflict` |
| Запрос без ключа | Обычное создание с `201` |

Идентичность запроса определяется SHA-256 сырых байтов тела. Поэтому изменение
пробелов или порядка JSON-полей считается другим телом. Запись действительна в
течение `IDEMPOTENCY_TTL`; фонового удаления нет, а просроченный ключ может быть
перезаписан при следующем использовании.

| Команда | Назначение |
|---|---|
| `make build` | Собрать все пакеты |
| `make run` | Запустить сервис |
| `make test` | Запустить проверки с `-race` |
| `make generate` | Перегенерировать Go-код из OpenAPI |

| `make migrate-down` | Откатить последнюю миграцию |

`contracts/` — неизменяемая копия контрактов курса. После централизованного
обновления контракта или для проверки воспроизводимости генерации выполните:

```bash
make generate
```

Сгенерированный файл `internal/generated/api.gen.go` коммитится вместе с
изменением контракта.

## Проверка

```bash
make build
make test
make generate
git diff --exit-code -- internal/generated/api.gen.go
```

`make test` запускает все Go-тесты с `-race`. `make migrate-down` откатывает одну
миграцию; для проверки полного отката повторите его для всех применённых версий,
после чего снова выполните `make migrate`.

Для ручной проверки readiness:

```bash
make migrate-status
curl -i http://localhost:8080/ready
tripgoctl environment stop
curl -i http://localhost:8080/ready   # ожидается 503
tripgoctl environment start
tripgoctl connect
# если DATABASE_URL изменился, перезапустите сервис в его терминале
curl -i http://localhost:8080/ready   # ожидается 200
```

После повторного запуска окружения `tripgoctl` актуализирует `.env`. Если адрес
PostgreSQL изменился, уже запущенный процесс его не перечитает: остановите
сервис, при необходимости снова выполните `make migrate`, запустите `make run`
и только затем проверяйте восстановление `/ready` до `200`.

Перед сдачей также проверяются следующие сценарии:

- create → get → finish → повторный finish даёт `201 → 200 → 200 → 409`;
- второй create для активного водителя даёт `409 driver_busy`;
- 20 конкурентных create одному водителю дают ровно `1 × 201` и `19 × 409`;
- два конкурентных finish дают `1 × 200` и `1 × 409`, а `finished_at` не
  перезаписывается;
- ошибка вставки в `trip_status_history` откатывает и изменение `trips`;
- одинаковый `Idempotency-Key` при конкурентных запросах создаёт одну поездку:
  один ответ `201`, остальные `200` с тем же `id`;
- `SIGTERM` прекращает приём новых запросов, дожидается активных в рамках
  `SHUTDOWN_TIMEOUT` и принудительно завершает процесс при исчерпании бюджета.

## Docker (бонус)

Миграции в образ не входят: перед первым запуском контейнера база должна быть
доступна, а `make migrate` — выполнен из репозитория.

Сборка образа:

```bash
docker build -f deploy/Dockerfile -t trip-service:lab1 .
docker image ls trip-service:lab1
```

При запуске из Docker Desktop адрес `localhost` внутри контейнера указывает на
сам контейнер. Поэтому для подключения к PostgreSQL на хосте адрес из `.env`
нужно заменить на `host.docker.internal`:

```bash
DB_URL="$(sed -n 's/^DATABASE_URL=//p' .env)"
DB_URL="${DB_URL/@localhost:/@host.docker.internal:}"

docker run --rm --name trip-service \
  --env-file .env \
  -e DATABASE_URL="$DB_URL" \
  -p 8080:8080 \
  trip-service:lab1
```

Проверка работающего контейнера:

```bash
curl -i http://localhost:8080/ready
```

Образ собирается в два этапа. В builder используется `golang:1.27-bookworm`,
бинарник компилируется с `CGO_ENABLED=0`, `-trimpath` и удалёнными отладочными
символами. Финальный слой основан на `distroless/static-debian13:nonroot`,
из артефактов приложения в него копируется только бинарник; исходников и Go
toolchain в итоговом образе нет. Процесс запускается от пользователя
`65532:65532`. `.dockerignore` исключает Git-метаданные, локальные `.env`, тесты
и служебные файлы из контекста сборки.

Для собранного `linux/amd64`-образа Docker 29.1.2 показывает `22.2 MB`
занимаемого места. Значение можно перепроверить командами
`docker image ls --tree trip-service:lab1` или `docker system df -v`.

## Решения

### Уровень изоляции транзакций

Используется PostgreSQL `READ COMMITTED`. Этого уровня достаточно для атомарной
записи связанных строк, а конкурентные бизнес-инварианты защищаются не
предварительным чтением, а ограничениями БД и условными SQL-операциями. Более
строгий уровень изоляции добавил бы лишние конфликты и необходимость повторять
транзакции, не давая преимуществ текущим сценариям.

### Менеджер транзакций

`TxManager.Do` открывает транзакцию и кладёт `pgx.Tx` в переданный `context`.
Репозитории получают исполнителя из контекста: внутри `Do` запрос выполняется
через транзакцию, снаружи — через `pgxpool`. Поэтому бизнес-слой не зависит от
`pgx` и не передаёт транзакцию аргументами методов.

Если callback возвращает `nil`, выполняется `COMMIT`. При ошибке или панике
отложенный вызов выполняет `ROLLBACK`, после чего ошибка или паника передаётся
выше. Вложенный `Do` обнаруживает уже существующую транзакцию и переиспользует
её без создания savepoint. Создание поездки и начальной записи истории, а также
завершение поездки и запись нового статуса выполняются внутри `Do`. Поэтому при
ошибке истории соответствующее изменение `trips` тоже откатывается.

### Одна активная поездка у водителя

Инвариант закреплён частичным уникальным индексом
`trips_driver_active_uidx` по `driver_id` только для строк со статусом
`active`. Поэтому два конкурентных запроса не могут создать две активные
поездки одному водителю. Репозиторий распознаёт PostgreSQL `SQLSTATE 23505` и
имя этого индекса, преобразует ошибку в доменную `ErrDriverBusy`, а HTTP-слой
возвращает `409 driver_busy`.

### Идемпотентность создания поездки

`IDEMPOTENCY_TTL` задаёт срок действия результата (в примере конфигурации — 24
часа). Резервирование ключа, создание поездки и начальной записи истории
выполняются в одной транзакции. Репозиторий хранит SHA-256 исходных байтов тела,
поэтому повтор с тем же ключом и побайтно тем же телом возвращает ранее
созданную поездку, а любое отличающееся тело приводит к конфликту. Конкурентное
резервирование сериализуется PostgreSQL через уникальный ключ и конструкцию
`INSERT ... ON CONFLICT`; после разрешения конфликта выполняется условное
обновление или чтение существующей записи. Фоновая очистка не выполняется:
после истечения TTL строка ключа переиспользуется при следующем запросе.

### Конкурентное завершение

Завершение выполняется одним условным запросом `UPDATE ... WHERE status =
'active' RETURNING ...`. Только один конкурентный запрос может изменить
строку. Если строка не обновлена, дополнительное чтение различает отсутствующую
и уже завершённую поездку, чтобы вернуть соответственно `404 trip_not_found`
или `409 trip_completed`. `finished_at` повторно не перезаписывается.

### Graceful shutdown

После `SIGINT` или `SIGTERM` сервис прекращает принимать новые запросы и вызывает
`http.Server.Shutdown`, а затем закрывает пул PostgreSQL. Обе операции используют
единый бюджет `SHUTDOWN_TIMEOUT`: время, потраченное на HTTP-drain, уменьшает
остаток на закрытие пула. Поскольку `pgxpool.Close` сам не принимает контекст,
он выполняется в отдельной горутине и ограничивается ожиданием по тому же
контексту. При исчерпании бюджета сервис пишет в лог сообщение о принудительном
завершении и возвращается из `main`.

### Health и readiness

`/health` проверяет только работоспособность процесса и не зависит от внешних
систем. `/ready` отдельно проверяет PostgreSQL с ограниченным по времени
контекстом. Это позволяет оркестратору не направлять трафик в процесс, который
жив, но временно не может обслуживать запросы к данным.
